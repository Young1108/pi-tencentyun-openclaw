# ADR-001：为微信插件补齐 ACP 持久会话适配

## 状态

已接受

## 日期

2026-08-29 02:19 CST

## 背景

目标是将本机 Pi 轻量桥迁移到腾讯云，继续使用腾讯官方 `openclaw-weixin` 插件处理微信登录、长轮询和消息发送，同时使指定私聊由 Pi 的 ACPX 持久会话处理。

已验证的 `@tencent-weixin/openclaw-weixin@2.4.6` 能把消息交给普通 OpenClaw Agent，但没有实现 ACP 配置绑定所需的会话匹配和初始化路径。仅在配置中添加 `type: "acp"` binding 会留下静默降级：微信可回复，但回复来自 OpenClaw 内置模型而不是 Pi。

## 决策

保留官方微信插件作为唯一微信通道，并使用仓库的 `scripts/patch-weixin-acp-binding.mjs` 在该插件的 `2.4.6` 已安装源码中增加最小 ACP 适配：私聊 ID 的 binding 匹配，以及命中时的 ACPX session 初始化。

脚本会校验包名、版本和源码锚点；首次应用时保存相邻备份。它不处理凭据，不改变微信 API 调用，也不引入新的常驻服务。

## 考虑过的替代方案

### 继续仅配置 `type: "acp"` binding

- 优点：没有源码变更。
- 缺点：微信插件不会消费该 binding，实际执行仍是内置 Agent。
- 否决原因：不满足 Pi 接管的目标，且表面上看起来像已成功。

### 恢复本机 Python 轻量桥

- 优点：已具备 Pi RPC、重试和输出截断能力。
- 缺点：重新引入独立微信收发实现和双通道状态，不再以官方插件为主。
- 否决原因：与迁移到 OpenClaw 官方微信通道的目标冲突。

### 维护微信插件上游 Fork

- 优点：改动可长期版本化。
- 缺点：需要额外发布、依赖维护和升级合并。
- 否决原因：当前只需为单台腾讯云实例补齐两个兼容点；先以显式、可审计补丁验证，若长期使用再上游提交或维护 Fork。

## 后果

- 每次重装或升级微信插件都要重新运行版本检查与补丁。
- 端到端验收必须同时观察微信回复和 ACPX/Pi session 证据，普通模型 HTTP 200 不再视为 Pi 验收。
- 上游提供原生 ACP binding 支持后，应删除本补丁并重新验收。
